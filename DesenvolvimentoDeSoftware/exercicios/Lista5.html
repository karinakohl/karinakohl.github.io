A2. Verdadeiro ou falso

Corrija as afirmações falsas.

1. Um Pull Request de 2.000 linhas é aceitável, desde que o autor escreva uma boa descrição.
2. Na revisão, a prioridade é verificar primeiro o estilo e só depois a corretude e a segurança.
3. Rótulos como nit:, suggestion: e issue: indicam a severidade de um comentário de revisão.
4. A revisão de código acontece antes do merge, enquanto a mudança ainda está em um Pull Request.
5. Aprovar com "LGTM" em dois segundos é aceitável quando o autor é experiente.
6. A revisão de código ajuda a compartilhar conhecimento e cria co-responsabilidade sobre o código.
7. Formatadores e linters automatizam as discussões de estilo, deixando a revisão humana para lógica, clareza e segurança.
8. Se uma chave de API foi commitada por engano, basta removê-la em um commit seguinte para o problema deixar de existir.

B1. A metáfora financeira e o quadrante de Fowler

(i) Na metáfora do débito técnico, o que representam o empréstimo, os juros e o principal? Dê um exemplo de cada.

(ii) Classifique cada frase no quadrante de Fowler (deliberado ou inadvertido × prudente ou imprudente):

#Frase
a"O que é um padrão de projeto?"
b"Agora que terminamos, entendemos como deveríamos ter feito."
c"Não temos tempo para design, lance assim."
d"Precisamos lançar agora e refatoraremos depois."
Resposta Esperada:

(i) Empréstimo: o atalho, escrever o código do jeito mais rápido e não do ideal para ganhar velocidade no lançamento. Juros: o custo contínuo, todo tempo futuro gasto lutando contra um código difícil de manter ("por que mudanças simples demoram tanto?"). Principal: o esforço de quitação, o trabalho de refatorar o código e deixá-lo no estado em que deveria estar desde o início (por exemplo, uma sprint para reescrever o módulo legado).

#Quadrante
aInadvertido e imprudente: falta de conhecimento; a equipe nem sabe que acumula dívida
bInadvertido e prudente: aprendizado natural, o débito surgiu da evolução do conhecimento
cDeliberado e imprudente: sabe que é ruim e ignora, o pior cenário
dDeliberado e prudente: decisão estratégica consciente, o débito como ferramenta

B4. O cálculo de frete "temporário"

A Black Friday se aproxima e o prazo é amanhã. Para lançar a promoção, um dev escreve:

if (data.equals("2026-11-27")) {
    frete = 0; // temporário
}

O dev sabia que o if era ruim, mas precisava lançar. Responda: (a) em que quadrante de Fowler está essa decisão? (b) Descreva os cinco passos do "pagamento dos juros" que podem acontecer nos meses seguintes. (c) Reescreva a solução como um débito prudente e bem gerenciado: o que deveria acompanhar esse código?

Resposta Esperada:
  • (a) Deliberado e prudente: o dev sabia que era um atalho e tinha uma razão de negócio (lançar a promoção).
  • (b) A data passa, mas o if continua no código; no ano seguinte alguém esquece a regra; ela conflita com uma nova promoção; o sistema dá frete grátis indevidamente; e o tempo investigando o bug e limpando o remendo é o pagamento dos juros.
  • (c) Um TODO rastreável com ID da tarefa, data e responsável; um item no backlog de débito com prazo de remoção; a regra em configuração (por exemplo, uma promoção com data de início e fim) e não escrita no código; e um teste que registre o comportamento esperado.

C2. Extract Method, Rename e constantes

Refatore o código abaixo aplicando Extract Method (de forma que calcularPrecoFinal vire uma orquestração de três passos), Replace Magic Number e Rename nas variáveis ambíguas. O comportamento deve permanecer idêntico.

Resposta Esperada: 
private static final double FATOR_DESCONTO_VIP = 0.9;
private static final double ALIQUOTA_IMPOSTOS = 0.15;

double calcularPrecoFinal(Pedido pedido) {
    double subtotal = calcularSubtotal(pedido.getItens());
    subtotal = aplicarDescontoVIP(pedido, subtotal);
    return adicionarImpostos(subtotal);
}

private double calcularSubtotal(List<ItemPedido> itens) {
    double subtotal = 0;
    for (ItemPedido item : itens) {
        subtotal += item.getQuantidade() * item.getPreco();
    }
    return subtotal;
}

private double aplicarDescontoVIP(Pedido pedido, double valor) {
    return pedido.isClienteVIP() ? valor * FATOR_DESCONTO_VIP : valor;
}

private double adicionarImpostos(double valor) {
    return valor + valor * ALIQUOTA_IMPOSTOS;
}
Cada método faz uma coisa e tem um nome que diz qual. Na IDE: Extract Method com Ctrl+Alt+M (IntelliJ) ou Alt+Shift+M (Eclipse); Rename com Shift+F6 ou Alt+Shift+R.

C5. Refatorar com segurança

O código abaixo não tem testes. Há um comportamento estranho: > 18 exclui quem tem exatamente 18 anos.

boolean isAdulto(Usuario u) {
    return u.getAge() > 18;
}
boolean podeVotar(Usuario u) {
    return u.getAge() > 18 && u.isCidadao();
}

Descreva, em ordem, o que você faria: (a) o primeiro passo antes de tocar no código, escrevendo o teste (use o padrão Arrange, Act, Assert); (b) a refatoração; (c) o que fazer com a suspeita de bug em > 18; (d) as mensagens dos commits, no padrão Conventional Commits.

Resposta Esperada:
  1. Teste de caracterização primeiro. Registrar o que o código faz hoje, mesmo que pareça estranho (Feathers, 2004). Rodar os testes: devem passar.
  2. Refatorar em passo pequeno. Extrair a constante IDADE_MAIORIDADE = 18 e usá-la nos dois métodos; rodar os testes de novo. Se falhar, reverter e tentar diferente.
  3. Não corrigir junto. Corrigir > para >= muda o comportamento, então vai em outro commit (e vira uma tarefa à parte, depois de confirmar a regra com quem conhece o requisito).
  4. Commits separados. Um por intenção: test: caracteriza isAdulto e podeVotar, refactor: extrai constante IDADE_MAIORIDADE e, depois, fix: considera maior de idade quem tem 18 anos.
@Test

    // Arrange
    var usuario = new Usuario(18);
    // Act
    boolean resultado = servico.isAdulto(usuario);
    // Assert: valor observado hoje, mesmo parecendo estranho
    assertFalse(resultado);
}

Resposta Esperada:

(i) a: REP (granularidade). b: CCP. c: CRP. d: SDP (estabilidade). e: SAP (estabilidade).

static <T extends Comparable<T>> T menor(List<T> itens) {
    T m = itens.get(0);
    for (T x : itens) {
        if (x.compareTo(m) < 0) m = x;
    }
    return m;
}

(d) Troque um print() de depuração por logging com níveis adequados e cite as quatro técnicas, além do depurador, que ajudariam em outros casos.

Resposta Esperada:
  • (a) Reproduzir: rodar localmente o teste que falhou. Formular hipótese: a lista notas chega vazia e a divisão por len(notas) dá zero. Testar a hipótese: inspecionar o estado real com um breakpoint. Corrigir e validar: corrigir a causa raiz, não o sintoma, e rodar o teste de novo.
  • (b) Em media_turma, notas = [] e total = 0; no call stack, a chamada vem de quem usou a função. A hipótese é confirmada.
  • (c) Guard clause abaixo. Retornar None ou lançar ValueError depende do contrato da função: None sinaliza "sem média" e exige que quem chama trate; exceção força o tratamento, mas pode ser pesada se turma vazia for um caso normal. O importante é documentar a escolha e testá-la.
  • (d) Logs sobrevivem em produção; prints, não. Níveis: DEBUG (detalhe fino), INFO (eventos normais), WARNING (algo estranho, mas segue), ERROR (falhou). Outras técnicas: rubber duck debugging, bisseção manual, git bisect (acha o commit que introduziu a regressão) e caso de teste mínimo.
import logging
log = logging.getLogger(__name__)

def media_turma(alunos):
    notas = [a.nota for a in alunos if a.presente]
    log.debug("notas das presentes=%s", notas)
    if not notas:                       # guard clause
        log.warning("turma sem alunos presentes")
        return None                     # ou: raise ValueError(...)
    return sum(notas) / len(notas)

E1. DevOps, CALMS e os três contínuos

(i) O que é DevOps e que problema do "muro entre Dev e Ops" ele busca resolver? O que significa cada letra de CALMS?

(ii) Indique se cada situação descreve integração contínua, entrega contínua ou implantação contínua:

#Situação
aCada push aciona build e testes automáticos, e a falha bloqueia o merge.
bO artefato fica sempre pronto para produção, mas a ida ao ar depende de um clique de aprovação.
cTodo commit aprovado vai à produção sem intervenção humana, com rollback automático.
dO pipeline roda lint, build e testes unitários, mas nunca chega a produção.
Resposta Esperada:

(i) DevOps é uma cultura e um conjunto de práticas que unem Desenvolvimento e Operações, com automação, medição contínua e colaboração, para entregar software com mais velocidade e confiança. Antes, Dev entregava um pacote "que funciona na minha máquina" e Ops o instalava sem contexto, gerando releases raras, arriscadas e cheias de surpresa. CALMS: Cultura (responsabilidade compartilhada), Automação, Lean (lotes pequenos, fluxo contínuo), Medição (decidir com métricas) e Sharing, compartilhamento (de conhecimento, ferramentas e incidentes).

(ii) a: integração contínua. b: entrega contínua (a decisão é de uma pessoa). c: implantação contínua (a decisão é do próprio pipeline). d: integração contínua.

E2. Lendo e corrigindo um workflow

Considere o workflow abaixo, em .github/workflows/ci.yml. (a) Explique o que fazem on, runs-on, uses e run. (b) Aponte pelo menos quatro problemas. (c) Reescreva a parte do deploy corrigida.

name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pytest
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh production
        env:
          TOKEN: ghp_abc123SECRET
Resposta Esperada:
  • (a) on: os eventos que disparam a execução. runs-on: a imagem da máquina virtual (runner) que executa o job do zero. uses: reaproveita uma action pronta. run: executa um comando de shell.
  • (b) Problemas: o deploy não tem needs: test, então roda em paralelo e mesmo com testes falhando; não há if restringindo a produção à branch main, então qualquer push ou PR faz deploy; o token está escrito no código e não em secrets; faltam o setup da linguagem e o cache de dependências, e uma permissions de menor privilégio. Também seria bom usar um environment com aprovação manual e proteger a main (CI verde e revisão obrigatórios, sem push direto).
permissions:
  contents: read
jobs:
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    environment: production
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./deploy.sh production
        env:
          TOKEN: ${{ secrets.DEPLOY_TOKEN }}
O token deve ser cadastrado em Secrets no GitHub, e o log mascara o valor. O token que já foi exposto precisa ser revogado.

E3. Escolhendo a estratégia de deploy

Para cada cenário, indique a estratégia mais adequada entre recreate, rolling, blue-green, canary e feature flag, e justifique citando downtime, custo, risco e facilidade de rollback.

#Cenário
aUma ferramenta interna, com pouco uso, que pode ficar fora do ar por alguns minutos de madrugada e precisa de custo baixo.
bUm sistema crítico que precisa trocar de versão de uma vez e voltar imediatamente se algo der errado, e a empresa aceita manter dois ambientes completos.
cUma mudança grande no checkout que será exposta a 5% dos usuários, depois 25% e depois 100%, comparando taxa de erro e latência.
dUma nova funcionalidade que já está em produção, mas desligada, para ser ligada primeiro a um time interno e desligada em segundos se necessário.
eUm serviço com várias instâncias, que deve ser trocado instância por instância, sem downtime, com custo baixo.
Resposta Esperada:
#Estratégia e justificativa
aRecreate: tem downtime e risco alto (todos afetados), mas custo baixo; aceitável aqui
bBlue-green: troca instantânea e rollback imediato (basta devolver o tráfego ao Blue), ao custo de dois ambientes; atenção ao banco compartilhado e a migrações compatíveis
cCanary: exposição gradual decidida por métricas; exige observabilidade, e o rollback é rápido (tira-se o tráfego do canary)
dFeature flag: deploy não é release; a flag liga a funcionalidade de forma gradual e age como kill switch. Custo: flags esquecidas viram dívida técnica
eRolling update: sem downtime e custo baixo; mas duas versões convivem durante a troca (a mudança precisa ser compatível) e o rollback é lento

E4. Contêineres e migração sem downtime

(a) Melhore o Dockerfile e o comando de publicação abaixo, explicando cada mudança (camadas e cache, imagem base, rastreabilidade da imagem).

FROM python:latest
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]

# no pipeline:
docker build -t ghcr.io/org/app:latest .
docker push ghcr.io/org/app:latest

(b) A coluna nome da tabela usuario precisa virar nome_completo, sem downtime, com o código antigo e o novo convivendo durante o deploy. Descreva os três passos da migração expandir e contrair. Por que reverter o código é fácil, mas reverter dados não é?

Resposta Esperada: 
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]

# no pipeline (SHA do commit como tag):
docker build -t ghcr.io/org/app:SHA_DO_COMMIT .
docker push ghcr.io/org/app:SHA_DO_COMMIT
  • (a) Copiar o requirements.txt antes do código reaproveita a camada de dependências no cache. A imagem base fixa e enxuta (slim, com versão definida) reduz tamanho e superfície de ataque e evita surpresas com latest. Tag pelo SHA do commit torna a imagem rastreável e imutável; a mesma imagem é construída uma vez e promovida de staging para produção.
  • (b) Expandir: adicionar nome_completo sem remover nome. Migrar: o código lê e escreve nos dois lugares e os dados existentes são copiados. Contrair: remover nome em um deploy posterior. Reverter código é voltar ao artefato anterior, mas só é seguro se o banco continua compatível; dados já alterados ou perdidos não voltam, então muitas vezes se prefere roll-forward (corrigir e publicar nova versão).

G1. Quando não refatorar, e a IA no meio

Um colega propõe usar um assistente de IA para "limpar" um módulo legado que funciona há anos, não tem testes e precisa ser entregue em uma semana. Argumente se isso é uma boa ideia. Use: (i) os cinco casos em que não se deve refatorar, (ii) onde a IA ajuda e onde exige cuidado, e (iii) as regras de uso que você exigiria.

Resposta Esperada (pontos de atenção):
  • Quando não refatorar: código legado estável que ninguém toca (juros zero); código descartável; código sem testes (escreva testes primeiro); prazo apertado (refatore depois, documentando a dívida com um TODO rastreável); código que você não entende (refatorar sem entender é reescrever errado). Este caso reúne vários deles.
  • Onde a IA ajuda: sugerir nomes melhores, propor Extract Method, rascunhar testes de caracterização, repetir a mesma mudança em muitos arquivos. Onde exige cuidado: mudar comportamento sem avisar, gerar diffs grandes demais para revisar, "melhorar" o que não precisava.
  • Regras de uso: testes verdes antes e depois (a IA acelera o passo, mas quem garante que o comportamento não mudou são os testes); um passo por vez; ler o diff como em qualquer PR; commit de refatoração separado.
  • Uma resposta razoável: não refatorar agora; primeiro escrever testes de caracterização (a IA pode rascunhá-los), entregar no prazo e registrar a dívida no backlog.

G2. Débito consciente é vantagem competitiva?

Uma startup precisa lançar um MVP em seis semanas. Argumente a favor e contra assumir débito técnico deliberado, explicando o que a equipe precisa fazer para que o débito seja uma ferramenta e não uma falência técnica. Relacione sua resposta com revisão de código, testes, CI/CD e feature flags.

Resposta Esperada (pontos de atenção):
  • A favor: código rápido valida a hipótese com usuários reais; se o produto valida, usa-se o lucro para pagar a dívida; se falha, não se perdeu tempo polindo código. É um débito deliberado e prudente.
  • Contra: sem controle, a dívida cresce sprint após sprint, a velocidade cai, 100% do tempo vai para corrigir bugs e 0% para criar valor: a falência técnica, o ponto sem retorno.
  • O que fazer: decidir conscientemente e registrar a dívida no backlog (torná-la visível); reservar tempo recorrente para pagá-la (dia da faxina, regra do escoteiro); manter testes automatizados mínimos para que refatorar seja possível depois.
  • Relação com as práticas: a revisão de código evita que o atalho seja inadvertido e espalha o conhecimento da dívida; o CI barra regressões mesmo com código apressado; feature flags separam deploy de release, permitindo lançar cedo e desligar rápido; o débito de testes é o mais perigoso porque gera medo de refatorar.
  • Débito técnico não é "código ruim": é uma ferramenta de gestão. Consciente e bem gerenciado é vantagem competitiva; ignorado é a falência do projeto.
